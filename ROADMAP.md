# CampusLens Roadmap

*Governed AI employees helping university leaders turn SIS data into human-centered action.*

Written for the Gloo AI Hackathon (Boulder, Oct 6-8, 2026). This is our build plan for
the two-week prototype in the proposal, the **President Weekly Student Success
Briefing**, which answers one question. *"What should I know about spring
registration?"*

The proposal (`PROPOSAL.md`) is the scope. This roadmap turns it into dated work and
gives every day a "done when" check. It also defines how code gets reviewed before
it counts.

## 3. Architecture in one page

We count seven layers, in the order data flows, and the model never touches a number
it did not receive.

1. The **fixture** holds 100 to 200 fictional Ellucian-style student records in JSON,
   generated by a script with a fixed seed so the planted demo values fall out
   exactly. Schema in §5.
2. The **metrics** are deterministic functions, one per contract row in §4,
   unit-tested against hand-computed expected values, with no model involvement.
3. The **findings object** is the metrics' output as structured data. Value,
   comparison, the source fields used, the row IDs behind it, and the definition
   text. This is the *only* data an AI employee receives.
4. The **AI employees** are three roles, and each has a permission set (fields it may
   request), a task template, and a system prompt. Each call is logged with the
   fields it received. A request for a field outside the role is refused by the
   permission layer *before* any model call, with the refusal as an audit event.
   - The **Chief of Staff** interprets the question, dispatches the two analyst
     tasks, and merges their findings into the seven-section briefing.
   - The **Enrollment Analyst** explains M1, M2, M7 against the prior-year baseline.
   - The **Student Success Analyst** explains M3, M4, M5 as barriers among the
     unregistered.
5. The **briefing** has seven sections in the proposal's order, and every sentence
   containing a number must trace to a finding. A test extracts every numeral from
   the briefing text and asserts it exists in the findings object, which makes the
   "AI may explain but not create metrics" rule structural.
6. The **human panel** carries an action plan (each action has an office), the
   leadership decision stated separately, and an Approve button. Approval creates a
   *simulated* follow-up task and an audit event, and nothing is sent anywhere.
7. The **audit log** holds append-only events. `question.asked`, `task.assigned`,
   `data.granted`, `data.refused`, `finding.produced`, `briefing.produced`,
   `decision.approved`, `task.created`, visible in the UI as a filterable list.

**Model provider.** We put one interface (`explain(findings, role) → text`) in front of
the provider, configured locally and never named in the code, so swapping the
provider is a configuration change. A replay mode serves recorded responses, so the
demo runs identically with the network down.

**Ports** are the UI dev server `5200` (`strictPort`) and the API `8910`.

## 4. Metric contracts

Every metric is recomputable by hand from the fixture rows, and the reviewer
hand-computes each one on Day 2 before any UI exists.

Timezone for all dates is America/Chicago, declared once and converted on ingest.
The **as-of date is the latest `registration_date` in the fixture**, not the wall
clock, so the demo never drifts.

| # | Metric | Formula | Source fields | Grain | Window + anchor | No data renders as | Planted value |
|---|---|---|---|---|---|---|---|
| M1 | Spring registration vs. same point last year | `registered_continuing(as_of) / registered_continuing(as_of − 1 year) − 1` | `enrollment.term`, `registration_status`, `registration_date`, `comparison.prior_year_equivalent_date`, `profile.continuing` | student | cumulative to as-of. Prior-year window anchored to the equivalent date | `--` when prior-year count is 0 | −4.8 % |
| M2 | Continuing students not yet registered | `count(continuing ∧ registration_status ≠ registered)` | `profile.continuing`, `enrollment.registration_status` | student | as-of | `--` when fixture empty. `0` is a real value | 42 |
| M3 | Of M2, financial hold under $1,000 | `count(M2 ∧ hold.category = financial ∧ ¬resolved ∧ amount < 1000)` | `hold.category`, `hold.amount`, `hold.resolved` | student | as-of | `--` | 18 |
| M4 | Of M2, no advising appointment this term | `count(M2 ∧ (last_appointment_date < term_start ∨ null))` | `advising.last_appointment_date`, `advising.appointment_status`, `term.start_date` | student | current term | `--` | 12 |
| M5 | Unresolved holds by responsible office | `count(¬resolved) group by responsible_office` | `hold.category`, `hold.responsible_office`, `hold.resolved` | office | as-of | empty table with "No unresolved holds" | fixture-defined |
| M6 | Days until registration closes | `term.registration_close_date − as_of` | `term.registration_close_date` | term | as-of | `--` if no close date | fixture-defined |
| M7 *(optional)* | Registered credit hours vs. prior year | `sum(registered_credit_hours) / prior_year_sum − 1` | `enrollment.registered_credit_hours` | term | as-of, prior-year equivalent | `--` when prior sum is 0 | fixture-defined |

We hold three contract rules everywhere. A zero denominator renders `--`, never
`0 %`, windows anchor to data timestamps, and the current in-progress bucket is
never aggregated.

## 5. Data boundary per AI employee

Fields are granted by role, and a request outside the role is refused before any
model call and logged as `data.refused`.

| Field group | Fields | Chief of Staff | Enrollment Analyst | Student Success Analyst |
|---|---|---|---|---|
| Student profile | `student_id` (pseudonymous), `program`, `class_level`, `continuing` | aggregate only | read | read |
| Enrollment | `term`, `registration_status`, `registered_credit_hours`, `registration_date` | aggregate only | read | read (status only) |
| Holds | `category`, `amount`, `responsible_office`, `hold_date`, `resolved` | aggregate only | **refused** | read |
| Advising | `advisor_id`, `last_appointment_date`, `appointment_status` | aggregate only | **refused** | read |
| Comparison | `prior_year_equivalent_date`, `prior_term_status`, `baseline` | aggregate only | read | read |
| Counseling / spiritual care | `counseling_notes`, `chaplain_contact` (present in the fixture *only* so the refusal is real) | **refused** | **refused** | **refused** |

**The two refusals we built for the demo.** First, the Enrollment Analyst's task
requests `hold.amount` and the permission layer denies it, logged. Second, the
executive types a question outside the approved use case ("Which students are in
counseling?") and the Chief of Staff refuses with a sentence, logged. Both are
automated tests run every day, not features added on Day 11.

## 8. Definition of done

The proposal's definition, plus our own bar. The prototype runs correctly and
harmlessly the first time, with no fixing by us.

**From the proposal**

- [ ] The full demonstration runs in four minutes.
- [ ] Every reported metric matches the fictional source data (hand-verified by the reviewer).
- [ ] Every major statement exposes its evidence (the numeral test passes, and the evidence drawer opens every claim).
- [ ] CampusLens produces one coherent briefing in the seven-section format.
- [ ] A human approves the leadership follow-up and the approval is logged.
- [ ] One unauthorized request is visibly refused and recorded.

**Verification matrix (Day 8, re-run Day 9)**

| Condition | How to induce | Pass criterion |
|---|---|---|
| Real path | Fresh database, live model, typed question | Briefing matches the golden run's numbers. Every claim opens to evidence |
| Empty data | Empty fixture | Every metric renders its contracted `--`. No crash. Briefing says no data |
| Provider down | Block the endpoint key or the network | "Model unavailable" state with retry. Metrics and evidence still render. Replay path offered |
| Replay | `--replay` with network off | Identical briefing to the golden run, twice in a row |
| Refusal | Both §5 refusal tests, plus a hand-typed out-of-scope question | Refused with a sentence. `data.refused` event visible in the audit view |
| Restart | Kill the API mid-briefing, restart | Audit log intact. The briefing can be regenerated. No duplicate `task.created` on re-approve |

**Our bar**

- [ ] Launched the way the demo launches, logs checked for errors and warnings.
- [ ] Nothing sends email, text, or case records. Nothing writes outside the project. No real student data anywhere.
- [ ] A fresh-eyes review has run and its findings are closed.
- [ ] `README.md` and `RUNBOOK.md` say how to run, stop, restart, and replay.

## 9. Risks and controls

| Risk | Control |
|---|---|
| The calendar in the proposal is two days too long | §0 compresses to 11 days with Day 9 as the reserve. Rehearsal is Oct 4-5, not on the event days |
| The model invents a number or a cause | Metrics computed in code. The model receives only the findings object. The numeral test fails the build |
| An AI employee sees more than its role | Permission sets per role, enforced before any model call. Every grant and refusal logged. The refusal is a daily test |
| Scope creep toward a general chatbot | The question field accepts one approved question. A second question is the refusal demo |
| Sensitive detail reaches leadership | Aggregates by default. Student-level rows appear only in the evidence drawer, and only fictional ones |
| The provider is dictated by the track rules | One provider interface. Replay mode makes the demo independent of any provider on the day |
| The demo depends on the network | Replay cache recorded Day 8. Backup video Day 10 |
| Eligibility | Rules read by Sep 28. Prior-work itemization in `PRIOR-WORK.md` |
| Christian framing becomes surveillance | Whole-person care principles only. No inference of faith or private spiritual condition. Counseling fields exist in the fixture solely to be refused |

## 10. Currently out of scope

Production Ellucian access or real student data · automatic changes to student
records · automatic email, text, or case creation · an unrestricted executive chatbot
· predictive retention modeling · financial-aid eligibility decisions · tutor,
international-student, or spiritual-care agents · a mobile application · a fourth AI
employee.

The second executive question is in. Next in line, now that the full briefing, evidence,
approval, and audit workflow runs reliably, is the Ellucian connector. One of us holds the
university's Ellucian data and access, so we are building the Ethos connector now,
pseudonymised at the university's edge, reading only the fields SCHEMA.md names and never
counseling or spiritual-care records. Real records enter only after the Registrar or data
steward authorizes it in writing and IT issues Ethos credentials. The other items return in
governed form. Approved tasks are sent by a named person, never unattended. Support
indicators are explainable rules that list their factors, never an opaque score. Financial
aid gets a review queue, and the determination stays in the aid office. Counseling stays
aggregate only, with the counseling director's authorization.
